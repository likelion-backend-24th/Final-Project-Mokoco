    - 의뢰자 A가 수리 요청 게시글을 등록한 상태

    8. 이미지 또는 동영상 첨부파일을 전송하고 상대방 화면에서 정상 조회되는지 확인한다.
    9. 거래 당사자가 계약 내용을 작성·확인하고 서명한다.

    11. 정상 결제가 확인된 후 거래 상태가 다음 단계로 진행 가능한지 확인한다.

### 주요 실패 흐름

- 실패 입력 또는 Dependency 상태:
    1. 동일 Post의 서로 다른 Proposal을 거의 동시에 채택 요청한다.
    2. 미채택 Proposal 또는 거래 비참여자가 ChatRoom 생성·접근을 요청한다.
    3. 다른 사용자가 임의의 `X-User-Email` 또는 사용자 ID를 요청에 넣어 권한 우회를 시도한다.
    4. 동일 Proposal/FixDeal에 ChatRoom 생성 요청을 반복한다.
    5. 결제 금액 또는 paymentId를 임의로 변경한다.
    6. 결제 완료 이전에 거래의 작업 시작 상태 전이를 요청한다.
    7. chat-service 또는 payment-service 의존 서비스가 일시적으로 응답하지 않는다.
- 안전한 사용자 결과와 저장되지 않아야 할 데이터:
    - 동일 Post에서는 활성 Proposal/FixDeal이 하나만 존재해야 한다.
    - 비참여 사용자는 ChatRoom·메시지를 조회하거나 전송할 수 없어야 한다.
    - 클라이언트가 전달한 사용자 신원 Header는 권한 판단에 사용하지 않는다.
    - 동일 Proposal/FixDeal에 중복 ChatRoom이 저장되지 않는다.
    - PortOne 실제 결제 정보와 서버 주문 정보가 일치하지 않으면 Payment를 생성하지 않는다.
    - 결제 완료 전에는 거래 상태가 작업 시작 단계로 변경되지 않는다.
    - 외부 서비스 호출 실패 시 중간 상태의 거래·결제 데이터가 잘못 저장되지 않아야 한다.
- 복구·재시도 기준:
    - 동시성 충돌은 클라이언트가 최신 상태를 다시 조회한 뒤 처리한다.
    - ChatRoom 중복 생성 요청은 기존 Room을 반환하거나 충돌 정책에 따라 안전하게 종료한다.
    - 외부 서비스 Timeout은 사용자에게 실패 결과를 반환하고 상태 변경을 커밋하지 않는다.
    - 결제 검증 실패 시 동일 `paymentId`에 대해 PG 상태 확인 후 재시도할 수 있다.
    - 배포 또는 DB Migration 실패 시 서비스 기동을 중단하고 DB 상태를 확인한 후 복구한다.

## Test 전략 요약

Mokoco의 Test는 단순 Service 단위 성공 여부가 아니라 다음 위험을 중심으로 구성한다.

- 인증·인가: JWT에서 검증된 `userId`만 사용자 신원으로 신뢰한다.
- 서비스 경계: 다른 Service의 Entity나 DB를 직접 참조하지 않고 내부 API와 ID 기반 논리 참조를 사용한다.
- 동시성: Proposal 채택, FixDeal 생성, ChatRoom 생성에서 중복 데이터가 만들어지지 않도록 Service Lock과 DB Constraint를 함께 검증한다.
- 멱등성: 동일 결제·동일 채팅방 생성 요청이 반복되어도 데이터가 중복 생성되지 않도록 검증한다.
- DB 정합성: 실제 운영 환경과 동일한 MySQL 기반 Testcontainers에서 Flyway Migration 및 Upgrade를 검증한다.
- 결제 신뢰성: 클라이언트 결제 결과를 직접 신뢰하지 않고 PortOne 서버 조회 결과와 서버 주문 데이터를 비교한다.
- 회귀: JWT 식별자 변경, chat-service 분리, Flyway 도입 이후 기존 사용자 흐름이 유지되는지 서비스별 CI에서 전체 Test를 실행한다.
- Demo: Sprint Goal에 해당하는 정상 사용자 흐름뿐 아니라 동시 요청·권한 위반·결제 실패 등 주요 실패 흐름을 함께 재현하고 Evidence를 남긴다.
