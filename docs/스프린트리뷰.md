| Done PBI | 실제로 사용할 수 있는 제품 결과 | 완료 근거 | Product Goal 진척 |

| 채택된 수리자와 1:1 채팅방 개설 | 의뢰자가 채택한 수리자와 거래용 채팅방을 생성하고, 의뢰자·수리자 양쪽에서 채팅방 목록과 상세 화면에 접근할 수 있음 | GitHub #36, #37, #38, #39 / 관련 Test 및 배포 환경 시나리오 확인 | 제안 채택 이후 거래 당사자 간 직접 소통이 가능한 흐름 연결 |
| 거래 시작 처리 | 채택으로 생성된 거래를 수리자 본인이 `MATCHED → PRODUCT_SENT` 상태로 전환할 수 있음 | GitHub #58, #59, #60 / 거래 시작 API 및 Acceptance Test | 제안 채택 이후 실제 수리 업무가 시작되는 상태 전이 확보 |
| 수리 진행 상태 관리 | 수리자가 `PRODUCT_SENT → REPAIRING`으로 거래 상태를 전환하고 의뢰자·수리자가 현재 진행 상태를 조회할 수 있음 | GitHub #61, #62, #63 / 상태 전이·권한·조회 Test | 거래 성립 이후 수리 진행 과정을 시스템 상태로 추적 가능 |
| 수리 완료 신청 | 수리자가 작업 완료 후 `REPAIRING → REPAIR_DONE`으로 완료 신청하고 의뢰자가 이를 확인할 수 있음 | GitHub #64, #65, #66 / 정상·권한·순서 위반 Acceptance Test | 수리 완료를 수리자가 일방적으로 확정하지 않고 의뢰자 확인 단계로 연결 |
| 결제 생성 및 상태 확인 | 완료 신청된 거래에 대해 의뢰자가 결제를 생성하고 결제 상태를 확인할 수 있으며, 서버가 총액·수수료 10%·수리자 정산액을 계산함 | GitHub #40, #43, #44, #45 / 결제 생성·중복·권한·상태 Test | 거래 완료 전에 결제 조건을 확인하는 안전거래 흐름의 기반 확보 |
| 결제 완료 전 거래 완료 차단 | 결제가 완료되지 않은 거래에서는 완료 수락을 진행할 수 없도록 거래 상태와 결제 상태가 연동됨 | GitHub #40, #44, #45 | 거래 완료와 결제 완료의 불일치를 방지하는 업무 규칙 확보 |

Sprint 2에서는 Sprint 1에서 구현한 `요청 → 제안 → 채택` 이후의 흐름을 확장하여, **채택 → 채팅방 → 거래 시작 → 수리 진행 → 완료 신청 → 결제**까지 실제 거래 과정이 연결되었다.

다만 Sprint 2의 결제 기능은 실제 PG 기반의 최종 결제·환불·정산 시스템 전체가 아니라, 결제 생성·상태·수수료 계산과 거래 완료 조건을 연결하는 수준을 포함한다. 실제 PG 연동 및 정산 지급·환불은 후속 범위로 관리한다.

Sprint 3에서는 Sprint 2의 상태 전이를 단순히 확장하는 데서 끝나지 않고 **계약 서명·결제 상태·거래 상태·정산 상태의 관계를 명확히 연결**하였다.

특히 거래 완료 시 정산 확정에 실패하면 상태 변경을 롤백하고, 동일 요청이 재시도되어도 중복 정산되지 않도록 하여 단순 기능 구현에서 실제 거래 안정성을 고려하는 방향으로 발전하였다.

또한 후기와 프로필 거래 이력을 추가하여 서비스가 단일 거래에서 끝나는 것이 아니라 **거래 이력이 다음 거래의 신뢰 정보로 축적되는 구조**로 확장되었다.
