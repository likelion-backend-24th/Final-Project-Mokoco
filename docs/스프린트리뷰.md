# Sprint 1

## 완료된 제품 결과와 진척

| Done PBI | 실제로 사용할 수 있는 제품 결과 | 완료 근거 | Product Goal 진척 |
| --- | --- | --- | --- |
| 회원가입 및 로그인 | 사용자가 회원가입 후 로그인하여 인증된 상태로 서비스를 이용할 수 있음 | GitHub Issue / PR / API 테스트 링크 | 인증된 사용자 기반의 서비스 이용 흐름 검증 완료 |
| 활동 지역 설정 | 사용자가 자신의 활동 지역을 설정·저장할 수 있음 | GitHub Issue / PR / API 테스트 링크 | 지역 기반 매칭을 위한 사용자 지역 정보 확보 가능 |
| 수리 요청 등록 | 의뢰자가 제품 정보와 고장 증상을 입력하여 수리 요청을 등록할 수 있음 | GitHub Issue / PR / API 테스트 링크 | 실제 수리 거래가 시작되는 요청 생성 기능 검증 완료 |
| 수리 제안 등록 | 수리자가 요청에 예상 가격·소요시간·설명을 포함한 제안을 등록할 수 있음 | GitHub Issue / PR / API 테스트 링크 | 사용자 간 수리 매칭을 위한 제안 기능 검증 완료 |
| 수리 제안 조회 | 의뢰자가 자신의 요청에 등록된 여러 수리 제안을 조회·비교할 수 있음 | GitHub Issue / PR / API 테스트 링크 | 여러 수리자 조건을 비교할 수 있는 흐름 검증 완료 |
| 수리 제안 선택 | 의뢰자가 하나의 수리 제안을 선택하여 거래 상대를 결정할 수 있음 | GitHub Issue / PR / API 테스트 링크 | 요청 → 제안 → 선택까지 핵심 거래 성립 흐름 검증 완료. 단, **거래 성립 이후 완료·취소·분쟁 처리 정책은 추가 정의 필요** |

완료 기준을 만족하지 못한 항목은 Done 표에 넣지 않고 Product Backlog로 돌아갑니다.

## 관찰·피드백·환경 변화

| 출처 | 관찰·피드백·환경 변화 | 제품에 미치는 영향 | 결정 |
| --- | --- | --- | --- |
| 이해관계자 피드백 | 수리 제안이 채택되었을 때 채택된 수리자뿐 아니라 **미채택된 수리자에게도 결과를 알려줄 것인지 정의되어 있지 않음** | 수리자가 자신의 제안 결과를 알 수 없어 계속 대기하거나 동일 요청을 진행 중인 것으로 오인할 수 있음 | 제안 채택·미채택 결과 알림 정책을 Product Backlog에 추가 |
| 이해관계자 피드백 | 수리 거래의 `완료` 상태를 누가 결정하는지 명확하지 않음 | 한쪽이 임의로 완료 처리할 경우 실제 작업 상태와 시스템 상태가 달라질 수 있음 | 수리자 완료 요청 → 의뢰자 완료 확인 구조 검토 |
| 이해관계자 피드백 | 거래 성립 후 의뢰자와 수리자가 취소하고 싶은 경우의 처리 규칙이 없음 | 일방 취소, 작업 진행 후 취소 등의 상황에서 분쟁 가능 | 거래 상태별 취소 가능 주체·조건·사유 정의 |
| 이해관계자 피드백 | 수리 결과, 비용, 작업 여부 등에 대한 의견 불일치 시 분쟁 처리 정책이 없음 | 실제 P2P 거래 과정에서 문제 발생 시 서비스 차원의 대응 기준이 없음 | 분쟁 신고 및 운영 처리 정책을 Product Backlog에 추가 |
| 리뷰 피드백 | 사용자 시나리오가 `요청 등록`, `제안 등록`, `제안 선택` 수준으로만 작성되어 실제 구현에 필요한 세부 행동과 상태 변화가 부족함 | 개발 단계에서 예외 상황, 권한, 상태 전이, 알림 등의 요구사항이 뒤늦게 발견될 가능성이 높음 | Actor의 행동 → 시스템 처리 → 상태 변경 → 상대방 결과까지 포함하도록 사용자 시나리오 구체화 |
| 리뷰 피드백 | 정상 흐름 위주로 작성되어 취소, 거절, 미채택, 분쟁 등 대안·예외 흐름이 충분히 정의되지 않음 | 구현 시 개발자가 상황별 동작을 임의로 판단하게 되어 기능 일관성이 떨어질 수 있음 | 정상 흐름뿐 아니라 Alternate / Exception Flow를 함께 정의 |
| 리뷰 피드백 | 구현된 기능이 개발 환경에서 동작하는 수준에 그치고 **실제 배포 환경까지 확인되지 않음** | 실제 사용 가능한 Increment인지 검증하기 어려우며 환경변수, CORS, 인증, DB 연결 등 배포 환경 문제를 발견하지 못할 수 있음 | 향후 Done 기준에 배포 및 배포 환경 동작 확인을 포함 |
| 제품 검토 | 지역 기반 수리 요청 조회 기능이 완료되지 않음 | 지역 기반 P2P 수리 매칭이라는 핵심 흐름이 완전히 연결되지 않음 | 해당 PBI를 Product Backlog로 반환하고 우선 구현 |

## Product Backlog 조정

| 조정 항목 | 변경 전 | 변경 후 | 근거·다음 확인 |
| --- | --- | --- | --- |
| 지역 기반 수리 요청 조회 | 이번 Sprint 완료 예정 | 미완료로 Product Backlog 반환 | 지역 설정 후 주변 요청 탐색이라는 핵심 사용자 흐름이 단절됨 |
| 수리 제안 채택 | 의뢰자가 제안 하나를 선택하면 거래 성립 | 제안 선택 시 선택된 제안은 `ACCEPTED`, 나머지는 `REJECTED` 또는 `NOT_SELECTED` 상태로 변경 | 하나의 요청에 여러 제안이 존재하므로 선택 결과를 명확하게 관리해야 함 |
| 제안 결과 알림 | 별도 정의 없음 | 채택된 수리자에게 채택 알림, 미채택된 수리자에게 미채택 결과 알림 제공 | 수리자가 제안 결과를 명확하게 확인할 필요가 있음 |
| 거래 상태 관리 | 제안 선택 시 거래 성립까지만 정의 | `ACCEPTED → IN_PROGRESS → COMPLETION_REQUESTED → COMPLETED` 등 거래 상태 정의 | 거래 성립 이후 실제 수리 진행 과정이 기존 시나리오에서 누락됨 |
| 거래 완료 처리 | 별도 정책 없음 | 수리자가 완료 요청 후 의뢰자가 완료 확인 | 한쪽의 일방적 완료 처리 방지 |
| 거래 취소 | 별도 정책 없음 | 사용자 역할과 거래 상태에 따라 취소 가능 여부 및 사유 정의 | 의뢰자·수리자 모두 취소 상황이 발생할 수 있음 |
| 분쟁 처리 | 별도 정책 없음 | 거래 분쟁 신고 및 관리자 확인 흐름 추가 | 완료·비용·수리 결과 등의 의견 불일치 대응 필요 |
| 사용자 시나리오 | 기능 단위의 단순 행동 및 기대 결과 중심 | Actor, 사전조건, 행동, 시스템 처리, 상태 변화, 알림, 실패·예외 흐름까지 구체화 | 실제 구현 단계에서 해석의 차이를 줄이기 위해 필요 |
| Done 기준 | 코드 구현 및 기능 동작 중심 | 테스트 통과 + 배포 완료 + 배포 환경에서 사용자 시나리오 검증까지 포함 | 실제 사용할 수 있는 Increment 기준 강화 |
