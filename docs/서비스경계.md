# 서비스 경계 정의서

## 후보·확정 경계

| Service | 책임 | 소유 데이터 | 분리·병합 근거 | 상태 |
| --- | --- | --- | --- | --- |
| api-gateway | 모든 요청의 단일 진입점, 서비스별 라우팅(`/api/auth`, `/api/posts`, `/api/payments` 등), CORS 처리 | 없음 | 프론트가 서비스별 포트를 몰라도 되게, CORS·인증 중복 관리 부담을 줄이기 위해 분리 | 구현 완료 |
| Next.js BFF | 브라우저 httpOnly 쿠키(access_token, user_email)를 백엔드가 신뢰하는 `Authorization`/`X-User-Email` 헤더로 변환. 멀티파트·웹훅·WebSocket은 이 계층을 거치지 않고 Caddy가 직결 | 없음 | 프론트 컴포넌트가 인증 헤더를 직접 다루지 않고 상대경로로만 호출하게 하기 위해 도입 (원래 계획엔 없던 계층 — Sprint 진행 중 추가) | 구현 완료 |
| user-service | 회원가입·로그인(이메일/Google/Kakao 소셜), JWT 발급, 역할 부여, 활동 지역 설정(Kakao Local API 역지오코딩), 이용약관 등 정책 페이지 정적 서빙 | 계정(User), SocialAccount, RefreshToken, 활동 지역(Region) | 지역 정보와 인증을 나눌 필요성을 못 느껴 병합. 정책 페이지는 별도 서비스 없이 정적 리소스로 흡수 | 구현 완료 |
| post-service | 게시글·사진, 수리 제안(Proposal), , 거래(FixDeal) 조회, **전자계약(작성·서명·상태전이 통합)**, **후기**, **이력서**, **프로필/거래내역**, **신고**, 관리자(글/신고 처리), **AI 작성 도움(Gemini 연동)** | Post, PostImage, Proposal, FixDeal, RepairContract/ContractSignature, Review/ReviewImage, Resume/ResumeCareer, Notification/NotificationSetting, Report | 게시글·계약·거래는 흐름이 강하게 연결돼 있어 하나의 서비스로 유지. 후기·이력서·신고도 별도 서비스로 분리할 만큼 독립적인 감사·확장 요구가 없어 흡수 | 구현 완료 |
| payment-service | 결제 생성·검증(PortOne V2), 수수료 계산, 에스크로 보관, **정산 확정**, 웹훅 수신·서명 검증 | Payment | 결제는 실제 PG 연동·금전 검증이 필요해 감사 요구 수준이 달라 분리 유지. 게시글·거래 상태는 post-service가 소유, payment-service는 조회만 함 | 구현 완료 |
| chat-service | 1대1 채팅, 거래 당사자 간 커뮤니케이 | ChatRoom/ChatMessage,  | 거래 도메인과 실시간 커뮤니케이션 도메인 분리, WebSocket, DB 소유권 분리 | 구현 완료 |

## 데이터 소유권

| 데이터 | 소유 Service | 생성·변경 책임 | 다른 Service에서 참조 방법 | 직접 DB 접근 |
| --- | --- | --- | --- | --- |
| User / SocialAccount / RefreshToken | user-service | 회원가입, 소셜 로그인 연동, 토큰 재발급 | email(주로 사용) 또는 userId(Long) — post-service는 UserClient(Feign)로 이메일↔ID 변환 | X |
| Region | user-service | 시/도·시군구·동 지역 데이터, `User.region` 연관관계 | regionCode 또는 `User.region_id`, 필요 시 내부 조회 API | X |
| Post / PostImage | post-service | 게시글 작성·수정·삭제, 작성자(authorEmail)·상태·지역 관리 | postId 논리 ID, `GET /posts/{id}` | X |
| Proposal | post-service | 제안 등록, 견적(estimatedPrice)·채택 여부(isAdopted)·이력서 첨부 여부(attachResume) 관리 | postId·proposalId 논리 ID, `GET /posts/{postId}/proposals` | X |
| FixDeal (거래) | post-service | 제안 채택 후 거래 생성, 당사자(requesterId, repairerId) 확정, 상태(MATCHED→REPAIRING→REPAIR_DONE→COMPLETED) 관리 — **상태 전이는 `ContractService.advance()`가 유일한 경로** | fixDealId·postId 논리 ID, `GET /fix-deals/{id}`, `GET /posts/{postId}/fix-deal` | X |
| RepairContract / ContractSignature | post-service | 채팅방 단위 계약서 작성(revision)·서명·상태(DRAFT→SIGNING→SIGNED) 관리 | chatRoomId, contractId 기반 API | X |
| Review / ReviewImage | post-service | 완료된 거래에 대한 후기 작성(postId 기준 1건) | postId 논리 ID, `GET /reviews`, `GET /reviews/by-post` | X |
| Resume / ResumeCareer | post-service | 수리자 이력서 작성·수정, 제안별 opt-in 공개(`attachResume`) | userEmail 논리 키, `GET /resume/{email}`(공개) | X |
| Notification / NotificationSetting | post-service | 제안 수신·채택·채팅 메시지 알림 생성, 유저별 수신 설정 | recipientEmail 논리 키 | X |
| Report | post-service | 게시글/유저 신고 접수, 관리자 처리(해결/기각) | reporterEmail/targetEmail 논리 키, `GET /admin/reports`(Admin) | X |
| Payment | payment-service | 결제 생성·검증(PortOne 재조회), 수수료 계산, 정산 확정(`settledAt`) | postId·portonePaymentId 논리 ID, `GET /payments/post/{postId}` | X |
| ChatRoom / ChatMessage | chat-service | 채팅방 생성·상태 관리, 메시지 생성·삭제를 `chat-service`가 전담 | `chatRoomId`, `fixDealId`, `proposalId`, `userId` 등 **ID 기반 참조 + 내부 API/DTO 통신** | X |

## 통신 방향·실패

| 호출 주체 → 대상 | 계약 | 왜 이 방향인가 | Timeout·실패 시 사용자 결과 |
| --- | --- | --- | --- |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |

| 호출 주체 → 대상 | 계약 | 왜 이 방향인가 | Timeout·실패 시 사용자 결과 |
| --- | --- | --- | --- |
| 사용자 → user-service | signUp, signIn, reissue, 소셜 로그인 | 계정·인증 정보는 user-service가 소유 | 인증 실패 401, 중복 회원 409 |
| 사용자 → user-service | `PATCH/GET /api/users/me/region` | 활동 지역 데이터의 소유자가 user-service | 잘못된 좌표 400, 지역 미설정 404 |
| user-service → 
외부 **Kakao Local API** | 역지오코딩(GPS 좌표 → 행정구역) | GPS 좌표를 행정구역으로 변환하는 책임을 user-service에 캡슐화. **VWorld에서 교체됨(AWS IP 차단)** | Timeout·API 오류 시 지역 저장 안 하고 실패 반환 |
| 사용자 → post-service | createPost, updatePost, deletePost, getPost, listPosts | 게시글 데이터는 post-service가 소유 | 인증 없음 401, 타인 수정 403, 없음 404 |
| 사용자 → post-service | createProposal, listProposals, adoptProposal, deleteProposal | 제안·채택 데이터는 post-service가 소유 | 본인 게시글에 제안은 현재 막혀있지 않음(문서상 규칙과 실제 구현 차이 있음), 이미 채택된 요청 409 |
| 사용자 → post-service | **계약서 통합 액션** `POST /chat-rooms/{roomId}/contract/{action}` (`request`·`sign`·`start`·`finish`·`accept`) | 계약·거래 상태는 채팅방(거래) 단위로 post-service가 소유하며 하나의 액션 엔드포인트로 통합(과거 FixDealService의 개별 PATCH 엔드포인트는 결제 우회 버그로 삭제됨) | 당사자 아님 403, 잘못된 상태 전이 409, **결제 미완료 시 `start` 거절 409** |
| post-service(advance `start`) → payment-service | `GET /payments/post/{postId}` | 작업을 시작하려면 결제가 끝나 있어야 하므로, post-service가 결제 완료 여부를 실시간 확인 | 결제 없음/미완료 → 409, payment-service 장애 시 502 |
| post-service(advance `accept`) → payment-service | `POST /payments/post/{postId}/settle` | 완료 확정 시 수리자 정산을 확정하는 책임은 payment-service에 있어, post-service가 트랜잭션 안에서 호출 | 정산 호출 실패 시 상태 전이도 함께 롤백(재시도 시 멱등하게 처리됨) |
| 사용자 → payment-service | `POST /api/payments`(결제 생성), `GET /payments/mine`, `GET /payments/post/{postId}` | 결제·수수료 계산은 payment-service가 소유. **결제 시점이 계약 서명 직후로 이동**(과거엔 수리 완료 신청 이후였음) | 금액 불일치 400, 중복 결제 409(`DUPLICATE_PAYMENT`), PortOne 장애 시 502 |
| payment-service(createPayment) → post-service | 내부 조회(금액·계약 상태 검증) | payment-service는 게시글·계약 상태를 소유하지 않아 결제 생성 전 확인 필요 | 게시글 없음 404, 금액 불일치 400 |
| payment-service → 외부 PortOne API | 결제 단건 조회(`GET /payments/{paymentId}`) | 프론트가 보낸 결제 성공 응답을 신뢰하지 않고, 실제 결제 여부·금액을 PortOne 서버 조회 결과로만 검증 | 조회 실패 시 재시도 후 최종 실패 처리, 금액 불일치 거절 |
| 외부 PortOne → payment-service | `POST /api/payments/webhook`(서명 검증, Caddy가 게이트웨이/BFF 없이 직결) | 브라우저가 결제 완료 응답을 못 받는 경우(네트워크 끊김)를 대비한 보조 안전장치. 프론트 확인 요청과 `portonePaymentId` 기준으로 멱등 처리 | 서명 검증 실패 시 처리 안 함, 중복 도착은 무시 |
| 사용자 → post-service | `createReview`(완료된 거래에 한해), `GET /reviews` | 후기 데이터는 post-service가 소유(**과거 문서엔 "미정"으로 되어 있었으나 확정 구현됨**, 별도 서비스 아님) | 미완료 거래 409, 비당사자 403, 중복 후기 409 |
| 사용자 → post-service | 이력서 작성·조회(`/resume`), 프로필/거래내역(`/profile`) | 이력서·프로필 데이터는 post-service가 소유 | 인증 없음 401(내 것), 타인 이력서·거래내역은 공개 조회 허용 |
| 사용자 → post-service | 신고 접수(`/reports`), 관리자 신고 처리(`/admin/reports`) | 신고 데이터는 post-service가 소유, 처리 권한은 Admin만 | 인증 없음 401, 비관리자 403 |
| 로그인 사용자 → post-service → 외부 **Gemini API** | AI 게시글 초안(`/ai/post-draft`), AI 계약서 초안(`/contract/ai-draft`) | 사진 분석·계약 초안 생성 책임을 post-service가 캡슐화. **문서에 전혀 없던 통신 경로 — 신규 추가** | AI 비활성화/한도초과 503, 응답 지연 504, 근거 없는 값 생성 시 422로 거절 |
| Client/API Gateway → chat-service | REST로 채팅방/메시지 조회, WebSocket(STOMP)으로 실시간 메시지 송수신 | 실시간 통신 책임을 `chat-service`가 소유하므로 클라이언트가 채팅 기능을 직접 호출 | 연결 실패 시 채팅 화면/메시지 전송 실패 안내, 재연결 가능 |
| post-service → chat-service | `proposalId`, `fixDealId`, `postId`, `requesterId`, `repairerId`를 DTO로 전달하여 채팅방 생성·동기화 | 거래 성립 여부는 `post-service`가 알고, 실제 `ChatRoom` 생성 책임은 `chat-service`가 가지기 때문 | Timeout 시 채팅방 생성/동기화 실패 응답. 거래 데이터와 채팅 데이터 간 불일치 가능성이 있어 재시도·보상 처리 필요 |
| chat-service → user-service | 사용자 ID/JWT 검증 API 호출 | 사용자 원본 데이터와 인증 책임은 `user-service`가 소유하므로 chat DB에서 직접 사용자 정보를 조회하지 않음 | 인증 확인 실패 시 WebSocket 연결 또는 채팅 접근 거부(`401/403`) |
| chat-service → 알림 기능 | 메시지 수신자 ID, `roomId`, `postId`, 메시지 내용 등을 전달 | 메시지 저장과 알림 발송 책임을 분리하고, 채팅 자체 성공 여부가 알림 시스템에 강하게 의존하지 않도록 구성 | 알림 실패 시 **채팅 메시지는 정상 저장**, 사용자에게 실시간 알림만 누락될 수 있음 |
