| 관련 Story | 로그인 / 회원 정보 / 게시글 / 제안 / 거래 / 결제 / 채팅 전반 |
| 관련 계약·Test | JWT Access Token, LoginUser, JwtUserIdTest, LoginUserSecurityTest, PaymentAuthenticationTest, UserClientAuthenticationTest |
| 재현·증상 | 게시글·제안·알림·결제 등 여러 도메인에서 authorEmail, repairerEmail, payerEmail 등을 사용자 소유권 판별 기준으로 사용. 이메일 변경 기능이 추가될 경우 기존 데이터의 소유자 식별이 깨질 수 있고, 서비스 간 요청마다 이메일 문자열을 전달·조회해야 하는 문제가 있었음 |
| 확인한 원인 | 이메일은 로그인 속성이지만 변경 가능한 비즈니스 데이터이며, MSA 전체에서 영구 식별자로 사용하기에는 부적절함. 서비스 간 참조는 불변 식별자인 User.id를 사용해야 하지만 초기 구현에서 JWT subject가 email로 설계되어 이후 도메인도 이메일에 의존하게 됨 |
| 조치·담당자 | JWT subject를 email에서 userId(Long)로 변경. 인증 이후 공통 LoginUser 객체를 생성하여 Controller/Service에서 사용자 ID와 권한을 사용하도록 수정. Post, Proposal, Notification, Resume, Review, Payment 등 소유권 필드를 단계적으로 userId 기반으로 전환하고 이메일 필드는 사용자 표시·이관 목적의 legacy 데이터로 제한 |
| 정상·실패 회귀 | 새 Access Token에서 userId가 정상 추출되는지 검증하고, 다른 사용자의 ID를 전달해도 서버가 JWT의 사용자 ID를 기준으로 권한을 판단하는지 Security Test 수행. 기존 이메일 기반 권한 우회 케이스가 발생하지 않는지 회귀 Test 통과 |
| Backlog·설계 조정 | 서비스 간 사용자 참조 규칙을 타 서비스 Entity/FK 참조 금지 + Long userId 논리 참조로 통일. 이메일·닉네임 등 변경 가능한 사용자 정보가 필요한 경우 user-service 내부 API를 통해 조회하도록 설계 기준 변경 |

| 시각·영향 | 2026-09-20 ~ 2026-09-21. 일부 API/BFF 흐름에서 사용자 이메일을 Header로 전달하면서 서버가 이를 사용자 식별에 사용할 가능성이 있었음 |
| 관련 Story | 인증이 필요한 전체 API / 서비스 간 내부 호출 |
| 관련 계약·Test | Authorization: Bearer ..., API Gateway RemoveRequestHeader, LoginUserSecurityTest, InternalServiceSecurityTest |
| 재현·증상 | 요청자가 X-User-Email과 같은 사용자 식별 Header를 임의로 설정할 수 있을 경우, 구현 방식에 따라 JWT 사용자와 Header 사용자가 달라질 가능성이 존재. 또한 외부 요청과 내부 서비스 호출용 Header를 명확하게 구분하기 어려웠음 |
| 확인한 원인 | 인증된 사용자 정보와 클라이언트가 직접 전달할 수 있는 HTTP Header가 혼재되어 있었음. 사용자 신원은 이미 JWT로 검증할 수 있으므로 별도 Header를 권한 판단 근거로 사용하는 것은 신뢰 경계를 넓히는 구조였음 |
| 조치·담당자 | API Gateway에 RemoveRequestHeader=X-User-Email, RemoveRequestHeader=X-Internal-Service-Key 필터를 추가해 외부에서 전달된 민감 Header를 제거. 사용자 신원은 JWT 검증 결과로 생성된 LoginUser만 신뢰하도록 변경하고, 서비스 간 내부 인증 키는 서버 측 Feign 설정에서만 생성하도록 분리 |
| 정상·실패 회귀 | 사용자가 임의의 사용자 ID/이메일 Header를 전달해도 권한이 변경되지 않는지 Test. 내부 API에 올바른 내부 서비스 인증 정보가 없는 경우 접근이 거부되는지 InternalServiceSecurityTest로 검증 |
| Backlog·설계 조정 | 인증 정책을 클라이언트 제공 identity를 신뢰하지 않는다는 원칙으로 문서화. 사용자 권한은 JWT, 서비스 권한은 내부 서비스 인증 메커니즘으로 각각 분리 |

## 제안 채택 동시성 문제: 동일 수리 요청에 복수 거래가 생성될 가능성

| 항목 | 기록 |
|---|---|
| 시각·영향 | 2026-09-18 ~ 2026-09-21. 하나의 수리 요청에 여러 제안이 존재하는 상태에서 거의 동시에 채택 요청이 들어올 경우 둘 이상의 Proposal이 채택되거나 FixDeal이 중복 생성될 가능성을 검토함 |
| 관련 Story | 제안 채택 / FixDeal 생성 / 채팅방 개설 |
| 관련 계약·Test | PATCH /posts/{postId}/proposals/{proposalId}/adopt, ProposalConcurrencyTest, FixDealServiceTest, ChatRoomConcurrencyTest |
| 재현·증상 | 애플리케이션 계층에서 hasAdopted 확인 후 proposal.adopt()를 수행하는 방식만 사용할 경우, 두 요청이 거의 동시에 기존 상태를 조회하면 모두 "아직 채택 없음"으로 판단할 수 있음. 그 결과 동일 Post에 두 개의 활성 거래가 만들어질 위험이 존재 |
| 확인한 원인 | SELECT → 조건 확인 → UPDATE/INSERT가 하나의 원자적 연산이 아니며, 단순 @Transactional만으로는 동시 요청을 직렬화하지 못함. 또한 애플리케이션 검증만 존재하면 우회 경로 또는 예상하지 못한 경쟁 상태를 DB가 막을 수 없음 |
| 조치·담당자 | 채택 대상 조회에 DB Lock을 적용하고, DB에도 활성 거래/채택 Proposal에 대한 Unique Constraint를 추가해 이중 방어. fix_deals에는 활성 거래만 유일성을 가지도록 generated column 기반 active_post_id, active_proposal_id를 사용하고 Proposal에도 채택된 post 기준 Unique 제약을 추가 |
| 정상·실패 회귀 | ProposalConcurrencyTest에서 동일 Post에 동시 채택 요청을 발생시켜 최종적으로 하나의 Proposal/FixDeal만 활성 상태가 되는지 확인. 중복 요청 시 정상 요청 하나만 성공하고 나머지는 정책에 따른 충돌 응답을 반환하도록 검증 |
| Backlog·설계 조정 | 동시성에 민감한 기능은 Service 검증 + Transaction/Lock + DB Constraint를 함께 적용하는 것을 공통 설계 원칙으로 추가. 결제·ChatRoom 생성 등 멱등성이 필요한 기능에도 동일한 방식 적용 |

## Flyway 도입: Hibernate ddl-auto 기반 스키마 관리로 인한 운영 DB 이력 부재

| 항목 | 기록 |
|---|---|
| 시각·영향 | 2026-09-20 ~ 2026-09-22. 기존 release 환경은 Hibernate ddl-auto:update를 사용해 DB Schema를 자동 변경하고 있었으며, 어떤 변경이 언제 적용됐는지 추적할 migration 이력이 없었음 |
| 관련 Story | 전체 서비스 DB Schema 관리 / 배포 안정성 |
| 관련 계약·Test | Flyway V1~V5, FlywaySchemaTest, FlywayUpgradeTest, MySQL Testcontainers |
| 재현·증상 | Entity 변경 시 Hibernate가 DB를 자동 변경하기 때문에 로컬·Test·운영 환경 Schema가 동일하다는 보장이 약하고, Unique Constraint나 generated column 등 중요한 DB 규칙이 코드 변경 이력으로 명확하게 남지 않음. 기존 운영 DB에 Flyway를 단순 활성화할 경우 이미 존재하는 테이블과 V1 CREATE TABLE이 충돌할 위험도 발생 |
| 확인한 원인 | 초기 개발 편의를 위해 ddl-auto:update를 사용했지만 프로젝트가 커지면서 Schema 변경이 중요한 비즈니스 규칙과 연결됨. 특히 동시성 제약, userId 전환, chat schema 변경은 Hibernate 자동 생성만으로 안전한 배포·데이터 이관을 보장하기 어려움 |
| 조치·담당자 | post-service, user-service, payment-service에 Flyway를 적용하고 ddl-auto를 validate로 변경. 신규 DB는 V1부터 순차 migration하고, 기존 release DB는 별도 production baseline/upgrade migration을 통해 기존 데이터를 유지하면서 Flyway 관리 체계로 편입하도록 설계 |
| 정상·실패 회귀 | MySQL Testcontainers를 사용해 빈 DB의 전체 migration 실행과 기존 V1 DB의 최신 버전 upgrade를 검증. FlywayUpgradeTest에서 기존 거래·채팅 데이터의 ID 및 FK가 migration 전후 유지되는지 확인 |
| Backlog·설계 조정 | 향후 Entity 변경 시 ddl-auto:update에 의존하지 않고 반드시 새로운 Flyway migration을 추가. 적용된 migration 파일은 수정하지 않고 이후 변경은 새로운 버전으로만 추가하는 규칙을 DoD에 포함 |

## 채팅 스키마 소유권 충돌: post-service와 chat-service가 동일 DB에서 Flyway를 실행할 위험

| 항목 | 기록 |
|---|---|
| 시각·영향 | 2026-09-21 ~ 2026-09-22. 채팅 기능을 chat-service로 분리하면서 기존 post_db 안의 채팅 테이블을 어느 서비스가 migration해야 하는지 불명확해짐 |

| 재현·증상 | post-service와 chat-service가 같은 post_db에 연결된 상태에서 두 서비스가 각각 Flyway를 실행하면 하나의 flyway_schema_history를 여러 애플리케이션이 경쟁적으로 관리하거나 서로 다른 migration set을 적용할 위험이 있음. 또한 과거 chat_room과 실제 Entity의 chat_rooms 테이블명 불일치도 발견됨 |

| Backlog·설계 조정 | 현재는 논리적 소유권: chat-service / 물리 Schema migration 소유권: post-service로 명시. 향후 chat DB를 물리적으로 분리할 경우 별도 migration 계획을 수립한 뒤 chat-service가 자체 Flyway history를 소유하도록 전환 |
