# AI 게시글·계약서 작성 보조 구현 기록

작성일: 2026-09-14

## 구현 결과

모델은 요청한 `gemini-flash-lite-latest`를 그대로 사용한다. 현재 계정에서 이미지 입력과 JSON 스키마 출력이 실제 호출로 확인되었다. Google 모델 목록 문서의 문자열 검색만으로 해당 별칭을 확인하지 못했으므로, 사용 가능 여부의 근거는 대상 계정 실호출이다.

- 게시글: 새로 첨부한 사진 1~5장과 현재 제목·내용·카테고리를 분석한다. 분석 완료 시 제목·내용·카테고리를 자동 입력하며, 제품·모델 후보·외관 관찰·추가 질문과 항목별 되돌리기를 제공한다.
- 계약서: 서버가 의뢰·채택 제안과 해당 방의 텍스트 대화를 시간순으로 조회해 13개 계약 항목으로 정리하고 자동 입력한다. 대화 선택·항목 적용 버튼은 제거했다. 금액은 AI 출력 대신 거래에 연결된 채택 제안의 estimatedPrice를 서버에서 직접 반영한다. 출처 인용·추가 확인 항목·상충 조건을 표시한다.
- AI는 게시글·계약을 저장하거나 서명하지 않는다. 기존 등록·버전 생성·문서 해시·양측 서명 흐름을 사용한다.
- 게시글과 계약서 모두 분석 시작 이후 사용자가 수정한 항목을 덮어쓰지 않는다. 게시글 분석 중 사진을 변경하면 결과를 적용하지 않고 재분석을 안내한다. 계약 상태가 변경되면 자동 입력하지 않는다. 자동 입력한 값이 유지되는 동안 항목별 되돌리기를 제공한다.
- AI 실패 시 수동 작성/등록을 계속할 수 있다.

## API와 실행 설정

| 프런트와 백엔드 경로 | 입력 |
|---|---|
| `POST /api/ai/post-draft` | multipart images, title, content, category |
| `POST /api/chat-rooms/{roomId}/contract/ai-draft` | JSON baseId, currentTerms, instructions |

Next.js 전용 Route Handler가 쿠키의 access_token을 Bearer로 전달한다. Gateway에 `/api/ai/**`를 추가했다. post-service가 토큰을 User 서비스에서 검증하며, 계약 문맥 조회 전에는 참여자·기준 버전·거래 상태를 검사한다. DB 조회에서 다른 방, 삭제 대화, 이미지·영상·시스템 메시지를 제외한다. 사용자가 메시지 ID를 지정할 필요가 없다.

환경변수 예시는 `backend/post-service/.env.example`에 있다. 이 파일을 Spring Boot가 자동으로 읽는 것은 아니므로 IntelliJ 실행 설정 또는 실제 서비스 프로세스 환경에 주입한다.

| 환경변수 | 기본값/의미 |
|---|---|
| GEMINI_API_KEY | 필수 키. GOOGLE_API_KEY도 대체 이름으로 지원 |
| GEMINI_MODEL | gemini-flash-lite-latest |
| AI_ASSIST_ENABLED | true. false면 AI 호출 중단, 수동 작성 유지 |
| AI_REQUESTS_PER_MINUTE | 계정별 3회 |
| AI_REQUESTS_PER_DAY | 계정별 UTC 일 20회 |
| AI_GLOBAL_REQUESTS_PER_DAY | 프로세스 전체 UTC 일 500회 |

사용자가 이미 설정한 IntelliJ post-service의 GEMINI_API_KEY를 확인했다. 키는 새 파일에 복사하지 않았고, 테스트 실행 시 프로세스 환경으로만 전달했다.

실행 반영에는 **post-service와 api-gateway 재시작**이 필요하다. 현재 실행 중인 IDE 서비스는 이 작업에서 종료·재시작하지 않았다. 프런트는 개발 서버에서 변경을 반영하거나 프로덕션 빌드 후 재시작한다.

## 검증 및 데이터 처리

- JPEG/PNG/WebP의 실제 디코딩 형식과 MIME을 비교한다. 이미지당 5MB, 합계 15MB, 최대 2,500만 화소를 검사한다.
- AI 전송용 이미지를 최대 긴 변 1,600px JPEG로 재인코딩하며 메타데이터를 전달하지 않는다. 영구 파일이나 AI 이력 테이블은 생성하지 않는다.
- 응답 크기, JSON 형태, 허용 필드·enum·길이·금액·날짜, 출처 ID 및 원문 인용 포함 여부를 서버에서 검사한다. 모델의 거절·출력 잘림·오류 응답을 사용자가 이해할 수 있는 오류로 변환한다.
- 금액은 서버에서 채택 제안을 조회해 직접 넣는다. 현재 입력이나 AI 출력에 다른 금액이 있어도 채택 제안 금액을 사용한다. 단, 응답을 기다리는 동안 사용자가 금액을 수정한 경우 프런트는 해당 수정값을 유지한다. 시작일·종료일은 기존과 같이 사용자가 입력한 날짜만 반영한다.
- AI를 기다리는 동안 DB 잠금을 유지하지 않는다. 호출 후 이전 조회 캐시를 비우고 최신 계약·거래 상태를 다시 확인한다. 실제 저장 시에는 기존 계약 서비스가 다시 최신 버전을 검사한다.
- 요청 ID, 기능, 상태 코드, 지연, 모델/프롬프트 버전과 토큰 사용량만 운영 로그에 기록한다. 키·사진·대화·계약 원문을 로그에 남기지 않는다.
- 공통 AI HTTP 요청은 20초 응답 제한, Next.js 프록시는 25초 제한이며 자동 재시도하지 않는다.

## 검증 결과

| 확인 항목 | 결과 |
|---|---|
| post-service 전체 Gradle test | 자동 입력 변경 후 **통과**. 일반 실행에서 실호출 테스트는 건너뜀 |
| AI 관련 테스트 | 미디어·삭제·타 방 메시지 제외 및 시간순 조회를 실제 H2 DB로 검증. 모델/현재 입력 금액 대신 채택 제안 금액이 반영됨을 검증 |
| Gemini 실제 호출 | 초기 구현 3건 통과. 이번 변경의 실제 계약 프롬프트도 추가 1건 통과: 합성 대화의 도색 제외 합의 및 제안 금액 50,000원 반영 확인 |
| 프런트 npm test | 기존 테스트 **13건 통과** |
| 프런트 npm run build | **통과**, 두 AI 라우트 생성 확인 |
| 변경 프런트 파일 ESLint | **통과** |
| 전체 프런트 ESLint | 기존 오류 2건: notifications/page.js의 purity, site-header.js의 set-state-in-effect. 이번 범위에서 변경하지 않음 |
| 브라우저 | 비로그인 상태에서 게시글 작성 접근 시 로그인 화면 이동 확인. 인증된 AI 화면 전체 흐름은 미검증 |

기존 ChatServiceTest가 NotificationService 생성자 인자 누락으로 전체 테스트 컴파일을 막고 있어, 해당 테스트에 mock 인자 1개만 추가했다. 누락된 프런트 의존성도 복원했으며 package.json/package-lock.json은 변경하지 않았다.

일반 `gradlew.bat test`는 비용이 발생하는 GeminiLiveTest를 건너뛴다. 별도 검증 시에만 키와 `GEMINI_LIVE_TESTS=true`를 프로세스에 설정하고 실행한다. 실제 호출 테스트는 합성 데이터만 전송한다.

## 남아 있는 검증 및 운영 한계

- 실제 로그인 두 계정으로 사진 분석 → 자동 입력 → 등록, 대화 자동 정리 → 계약 자동 입력 → 양측 서명을 브라우저에서 검증해야 한다. 이번 계약 변경 반영에는 post-service 재시작 및 화면 새로고침이 필요하다.
- 텍스트 500개, 직렬화한 전체 자료 60,000자까지 자동 정리한다. 초과하면 일부 대화를 몰래 생략하지 않고 수동 작성을 안내한다. 더 긴 대화의 분할 요약은 아직 미지원이다.
- 계획서의 실제 사진 12건·계약 시나리오 10건 품질 평가는 아직 수행하지 않았다. 합성 입력의 실호출 성공이 다양한 실제 제품의 분석 정확도를 보장하지 않는다.
- 사용량 제한은 현재 단일 프로세스 메모리 기준이며 재시작하면 초기화된다. 다중 인스턴스 운영 전 공유 한도 저장소를 적용하고, 공급자 계정의 예산/쿼터도 별도로 설정해야 한다. 호출 횟수 제한은 금액 기준 과금 상한이 아니다.
- 사진 수정 화면에서는 새로 첨부한 파일만 분석한다. 기존 저장 이미지 재분석은 미지원이다.
- 금액은 채택 제안에서 자동 입력되며 날짜는 직접 입력한다. 다른 AI 제안 조건도 사용자 검토와 기존 양측 서명이 필요하다.
- latest 별칭의 향후 모델 변경, 실제 응답 지연과 실패율은 운영 로그로 확인해야 한다.
