# 공통 완료 기준(Definition of Done, DoD)

> **작성·동기화 메타정보**
>
> * Notion 원본 URL: `[팀 Notion 페이지 URL]`
> * Snapshot 기준 시점: `[Sprint N Review 종료 / Week 4 최종 확정 시점]`
> * 동기화 시각: `[YYYY-MM-DD HH:mm KST]`
> * 직접 편집 금지: Git Snapshot은 직접 편집하지 않고, Notion 원본을 수정한 뒤 다시 동기화한다.

공통 완료 기준(Definition of Done, DoD)은 Product Backlog Item(PBI)을 단순 구현 완료가 아닌 **검증 가능한 제품 결과**로 인정하기 위해 팀 전체가 공통으로 적용하는 품질 기준이다.

각 PBI는 아래 기준을 만족해야 `DONE`으로 판정하며, Sprint Review 전에 각 항목을 확인할 수 있는 Evidence를 남긴다.

## 1. 공통 완료 조건

* [ ] 정의된 Acceptance Criteria를 모두 만족한다.
* [ ] 정상 사용자 흐름이 요구사항대로 동작한다.
* [ ] 주요 실패 흐름 및 예외 상황이 정의된 정책대로 처리된다.
* [ ] 인증·인가가 필요한 기능은 권한 정책이 정상 적용된다.
* [ ] 사용자 입력값에 대한 Validation이 적용되어 있다.
* [ ] 데이터 상태 변경 시 정의된 비즈니스 규칙을 위반하지 않는다.
* [ ] 서비스 간 연동이 필요한 경우 API 계약에 맞게 동작한다.
* [ ] 기존 기능에 의도하지 않은 영향을 주지 않는다.
* [ ] 요구사항이 변경된 경우 관련 Issue 및 요구사항 문서가 함께 갱신되어 있다.
* [ ] Review 과정에서 발견된 필수 수정 사항이 반영되어 있다.

## 2. Test 완료 조건

* [ ] 핵심 비즈니스 로직에 대한 단위 Test가 작성되어 있다.
* [ ] Repository / Service / API 등 필요한 계층의 통합 Test가 작성되어 있다.
* [ ] 성공 Case뿐 아니라 주요 실패 Case도 Test한다.
* [ ] 인증·인가가 필요한 기능은 권한 실패 Case를 Test한다.
* [ ] 상태 전이가 존재하는 경우 허용된 전이와 허용되지 않은 전이를 Test한다.
* [ ] 중복 요청 또는 동시 요청의 영향을 받는 기능은 필요한 경우 멱등성·동시성 Test를 수행한다.
* [ ] 기존 기능에 영향을 미치는 변경은 관련 회귀 Test를 수행한다.
* [ ] 실제 운영 DB와 차이가 중요한 기능은 가능한 경우 MySQL/Testcontainers 기반으로 검증한다.
* [ ] 전체 Test 실행 결과가 성공한다.

## 3. 보안 및 민감정보

* [ ] 인증이 필요한 API는 인증되지 않은 사용자의 접근을 차단한다.
* [ ] 사용자 본인 또는 특정 역할만 수행할 수 있는 기능은 인가 검증을 수행한다.
* [ ] 다른 사용자의 ID를 임의로 전달하여 권한을 우회할 수 없는지 확인한다.
* [ ] 비밀번호, Access Token, Refresh Token, API Key 등의 민감정보가 응답·로그·Repository에 노출되지 않는다.
* [ ] 환경별 Secret은 소스코드에 직접 작성하지 않는다.
* [ ] 해당 사항이 없는 경우 Evidence에 `N/A`와 사유를 기록한다.

## 4. 서비스 간 계약 및 데이터 소유권

MSA 서비스 간 연동이 포함된 PBI는 다음 기준을 추가로 만족해야 한다.

* [ ] 각 데이터의 소유 Service가 명확하다.
* [ ] 다른 Service의 DB를 직접 조회하거나 수정하지 않는다.
* [ ] 서비스 간 데이터는 ID 기반 논리 참조를 사용한다.
* [ ] 서비스 간 호출은 정의된 API/DTO 계약을 사용한다.
* [ ] 요청·응답 DTO 변경 시 호출 Service와 대상 Service의 계약을 함께 확인한다.
* [ ] Timeout 또는 대상 Service 장애 시 처리 정책이 정의되어 있다.
* [ ] 중복 호출 가능성이 있는 API는 필요한 경우 멱등성이 보장된다.

## 5. Review 및 문서화

* [ ] 구현 내용에 대한 Pull Request 또는 코드 Review가 완료되어 있다.
* [ ] Review에서 발견된 필수 수정 사항이 반영되어 있다.
* [ ] API가 추가·변경된 경우 API 명세가 최신 상태로 유지된다.
* [ ] 주요 비즈니스 규칙이 변경된 경우 요구사항 문서에 반영되어 있다.
* [ ] 서비스 책임 또는 데이터 소유권이 변경된 경우 관련 설계 문서를 수정한다.
* [ ] DB Schema 변경 시 Migration 파일과 관련 문서를 갱신한다.

## 6. 통합 및 Demo

* [ ] 프론트엔드와 백엔드가 실제 API를 기준으로 정상 연동된다.
* [ ] 서비스 간 호출이 필요한 기능은 통합 환경에서 정상 동작한다.
* [ ] 정상 사용자 시나리오를 처음부터 끝까지 수행할 수 있다.
* [ ] 주요 실패 시나리오에서도 정의된 사용자 결과가 나타난다.
* [ ] Sprint Review에서 실행 가능한 상태로 준비되어 있다.
* [ ] Demo 실행 결과 또는 화면·영상·Test 결과 등의 Evidence가 존재한다.

# PBI별 Evidence

각 PBI는 아래 표에 완료 근거를 기록한다.

`DONE`은 단순 구현 완료가 아니라 **AC → Test → 권한/보안 → Review → 계약/문서 → 통합/Demo**까지 필요한 기준을 만족한 경우에만 판정한다.

| PBI                 | AC Evidence       | Test·회귀 Evidence     | 권한·민감정보 Evidence               | Review Evidence    | 계약·문서 Evidence             | 통합·Demo Evidence          | 실행 근거                      | 판정                |
| ------------------- | ----------------- | -------------------- | ------------------------------ | ------------------ | -------------------------- | ------------------------- | -------------------------- | ----------------- |
| `[Issue 링크 / PBI명]` | `[Test/PR/화면 링크]` | `[Test 코드·CI 결과 링크]` | `[Security Test 링크 또는 N/A 사유]` | `[PR / Review 링크]` | `[API 명세·문서 링크 또는 N/A 사유]` | `[Demo 영상·화면·통합 Test 링크]` | `[전체 Test 통과 / Demo 확인 등]` | `DONE / NOT_DONE` |

## 판정 기준

**DONE**

* 해당 PBI에 필요한 공통 DoD를 모두 만족한다.
* 필수 Evidence가 존재한다.
* Test 및 통합 확인이 완료되었다.
* 미해결 Critical/Major 문제가 없다.

**NOT_DONE**

다음 중 하나라도 해당하면 `NOT_DONE`으로 판정한다.

* Acceptance Criteria 일부 미충족
* 필수 Test 미작성 또는 Test 실패
* 인증·인가 정책 미검증
* 필수 Review 미완료
* 서비스 간 API 계약 불일치
* 통합 또는 Demo 실패
* 요구사항 변경 내용이 문서에 반영되지 않음

단, 특정 항목이 해당 PBI와 관련 없는 경우 빈칸으로 두지 않고 **`N/A - 사유`**를 기록한다.
