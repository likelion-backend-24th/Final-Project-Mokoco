# 제품 요구사항 정의서

## 1. 사용자 문제·Product Goal·성공 기준

| 항목 | 정의 |
| --- | --- |
| 사용자 문제 | 전자제품이 고장 났을 때 사용자는 가까운 지역에서 수리 가능한 사람을 찾기 어렵고, 개인 수리자의 실력·가격·소요시간·신뢰도를 비교하기 어렵다. 반대로 수리 능력을 가진 개인은 주변의 수리 수요를 발견하고 자신의 기술을 활용할 기회가 부족하다. |
| Product Goal | 지역 내 전자제품 수리 수요와 개인의 수리 능력을 연결하여, 사용자가 거리·가격·수리 경험·후기 등을 기준으로 적합한 수리자를 찾고 수리 거래를 완료할 수 있도록 한다. 동시에 수리 능력이 있는 사용자는 주변의 수리 요청을 확인하고 자신의 조건에 맞는 요청에 수리 제안을 할 수 있도록 한다. |

### Release 성공 기준

- 사용자는 자신의 지역을 기준으로 주변의 수리 요청을 조회할 수 있다.
- 사용자는 고장 난 전자제품의 정보와 증상을 입력해 수리 요청을 등록할 수 있다.
- 다른 사용자는 해당 요청에 예상 수리 비용과 소요시간을 포함한 수리 제안을 등록할 수 있다.
- 수리 요청 작성자는 여러 수리 제안을 비교하고 하나를 선택할 수 있다.
- 제안이 선택되면 의뢰자와 수리자 간 하나의 수리 거래가 성립한다.
- 거래 당사자는 수리 진행 상태를 확인할 수 있다.
- 수리가 완료되면 거래 당사자가 상대방에 대한 후기를 작성할 수 있다.
- 사용자는 자신이 작성하지 않은 수리 요청을 임의로 수정하거나 삭제할 수 없다.
- 수리 요청 작성자만 해당 요청의 수리 제안을 선택할 수 있다.
- 하나의 수리 요청에서는 동시에 하나의 수리 제안만 최종 선택될 수 있다.
- 완료되거나 취소된 거래에 대해 중복 처리되지 않아야 한다.
- 권한 없는 접근, 이미 처리된 제안 선택, 잘못된 상태 변경 등 주요 실패 흐름을 시스템이 거절해야 한다.

## 2. 대상 사용자·Release 범위

### 대상 사용자

| Actor | 목표·책임 |
| --- | --- |
| 사용자(User) | 지역 기반 수리 플랫폼을 이용하는 기본 사용자. 의뢰자 또는 수리자로 참여할 수 있다. |
| 의뢰자(Requester) | 현재 거래에서 고장 난 제품의 수리를 요청하고 제안을 비교하여 수리자를 선택한다. |
| 수리자(Repairer) | 현재 거래에서 다른 사용자의 수리 요청을 확인하고 수리 조건을 제안하며 선택된 경우 수리를 수행한다. |
| 관리자(Admin) | 사용자·게시물·신고 등을 관리하고 플랫폼의 기본적인 운영 정책을 관리한다. |

## 범위

| 구분 | 내용 |
| --- | --- |
| 현재 Release | 회원가입/로그인 → 활동 지역 설정 → 수리 요청 등록 → 지역 기반 요청 조회 → 수리 제안 → 제안 비교/선택 → 매칭 → 수리 상태 관리 → 완료 → 후기까지 개인 간 수리 거래의 핵심 흐름을 연결한다. |
| 후속 Product Backlog 후보 | 실시간 채팅, 사진 다중 업로드, 찜, 사용자 인증, 전문 분야 등록, 지도 기반 탐색, 결제, 에스크로, 신고/분쟁 처리, 알림, 추천 알고리즘, 거래 취소 정책 고도화 |
| 제외 범위 | 실제 PG 결제, 사용자 간 정산, 플랫폼 수수료, 세금 처리, 택배 연동, 실제 본인 인증, 자격증 진위 검증, 플랫폼의 수리 품질 보증, 손해배상 및 분쟁 중재 |

> **수리가 필요한 사용자가 주변의 수리 가능한 개인에게 요청을 올리고, 제안을 받은 후 한 명을 선택하여 수리 완료까지 거래를 진행할 수 있다.**

## 수리 요청 상태

```
OPEN
수리 제안을 받고 있는 상태
   ↓
MATCHED
수리자가 선택된 상태
   ↓
IN_REPAIR
실제 수리가 진행 중인 상태
   ↓
COMPLETED
수리가 완료된 상태
```

취소를 포함하면:

```
OPEN ───────────→ CANCELED
 ↓
MATCHED ────────→ CANCELED
 ↓
IN_REPAIR
 ↓
COMPLETED
```

| 제품 카테고리 | 스마트폰, 노트북, 태블릿, PC, 키보드 등 수리 대상 제품의 분류 |
| 수리 요청(Repair Request) | 사용자가 고장 제품과 증상에 대한 정보를 작성하여 수리를 요청하는 게시물 |
| 수리 제안(Repair Offer) | 다른 사용자가 수리 요청에 대해 예상 비용, 예상 소요시간, 작업 설명 등을 제시하는 행위 및 정보 |
| 제안자(Offerer) | 특정 수리 요청에 수리 제안을 등록한 사용자 |
| 매칭(Match) | 의뢰자가 하나의 수리 제안을 선택하여 수리자를 확정하는 것 |
| 수리 결제(Repair Transaction) | 매칭 이후 의뢰자와 수리자 사이에서 진행되는 수리 과정에 따른 결제 |
| 수리 상태(Repair Status) | 현재 수리 거래가 어느 단계에 있는지를 나타내는 상태 |
| 완료 거래 | 수리자가 수리 작업을 완료하여 `COMPLETED` 상태가 된 거래 |
| 후기(Review) | 완료된 거래에 참여한 사용자가 상대방의 거래 경험을 평가한 정보 |
| 평점(Rating) | 거래 후기에서 상대방에 대해 부여한 수치형 평가 |
| 희망 가격 | 의뢰자가 수리를 맡길 때 고려하는 예상 또는 최대 비용 |
| 예상 수리비 | 수리자가 수리 제안 단계에서 제시한 예상 작업 비용 |
| 예상 소요시간 | 수리자가 예상하는 수리 작업 소요시간 |

# 8. Release에서 반드시 검증해야 할 실패 시나리오

### 본인의 요청에 본인이 제안

```
A가 수리 요청 작성
↓
A가 자신의 요청에 제안

→ 거절
```

### 타인이 요청 수정

```
A의 수리 요청
↓
B가 수정 요청

→ 거절
```

### 이미 매칭된 요청에 다른 사람 선택

```
A 요청

B 제안 → 선택 완료

C 제안 → 선택 시도

→ 거절
```

### 거래와 관계없는 사용자가 상태 변경

```
A = 의뢰자
B = 수리자
C = 제3자

C가 거래 상태 변경

→ 거절
```

### 완료 전 후기

```
MATCHED / IN_REPAIR

후기 등록 요청

→ 거절
```

### 중복 후기

```
COMPLETED
↓
A → B 후기 작성
↓
A → B 후기 다시 작성

→ 거절
```
